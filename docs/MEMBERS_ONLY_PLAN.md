# Members-only Basetool — removing the anonymous and guest surface

The owner's brief, 2026-09-04: every anonymous and guest access is removed; every user holds at
least member rights; the only public page is the landing page; an unauthenticated visitor sees no
internal data (no Einsätze, nothing); API and UI are closed and hardened accordingly; Keycloak is
hardened; the role model, the wiki, the README, the security policy and the knowledge base are
updated; logged-in members see no regression; everything is covered by tests, and the public API is
pinned by tests so that nobody without a login can read anything through it.

This document is the plan. It has four parts: the target state (§2), the decisions the owner has
to take before work starts (§3), the complete inventory of what exists today and has to go (§4),
and the work packages with their tests, documentation and rollout order (§5–§10). §11 records the
review the draft went through and what it changed.

## 1. Definitions

|         Term          |                                                                                                                                                                                              Meaning in this plan                                                                                                                                                                                              |
|-----------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Anonymous**         | A caller with no JWT (backend) or no session (frontend). Spring represents it as `AnonymousAuthenticationToken`.                                                                                                                                                                                                                                                                                               |
| **`GUEST` role**      | The backend-seeded application role `GUEST` (`Roles.GUEST`, `DataInitializer:87`, code stamped by `V73`) with an empty authority set; the fallback `UserReconciliationService` assigns when a token carries no known realm role. It is **not** a realm role in the sanitized production reference (`docs/keycloak/realm-config.reference.json`); it exists as a realm role only in the two test realm exports. |
| **Outsider**          | Today's term for "anonymous or role-less `GUEST`" on the mission surface (`AuthHelperService.isMemberOrAbove() == false`). The term disappears with this plan.                                                                                                                                                                                                                                                 |
| **Guest participant** | A `mission_participant` row with `user_id IS NULL` and a `guest_name` — a named person who is not an account. Created today either by an anonymous self-sign-up (capability token, REQ-SEC-018) or by a logged-in user through the crew board's free-text name. After this plan: an **external participant**, recorded by mission leadership.                                                                  |
| **Role-less token**   | An authenticated JWT whose realm roles map to no application role. Today it is mapped to `GUEST`; after this plan it is refused (`403 NO_ROLE`).                                                                                                                                                                                                                                                               |
| **Landing page**      | `GET /` for an unauthenticated visitor. Today it renders the seven-day mission grid; after this plan it renders **no data** and mints **no session**.                                                                                                                                                                                                                                                          |
| **Public surface**    | The exact list of paths that stay reachable without a login (§2). Everything not on it requires authentication **and** a member role.                                                                                                                                                                                                                                                                          |

### 2.2 Backend — the only `permitAll()` matchers

The main chain (`backend/.../config/SecurityConfig.java`):

|                   Path                    |                                                                                                  Why it stays                                                                                                  |
|-------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `GET /api/v1/app/version-policy`          | The Android forced-update gate (REQ-API-010 / REQ-SEC-037, owner decision 2026-08-24). Three integers and a public release URL; an app too old to log in must still learn that it is too old. Decision D2.     |
| `GET /api/v1/terms/document`              | The Terms-of-Use wording (ADR-0138 / REQ-SEC-028). It is the same text the public `/terms` page renders, so it publishes nothing; the public legal page cannot be served without it. Decision D3.              |
| `/internal/**`                            | The Keycloak SPI's account-existence precheck (REQ-SEC-022). Machine-to-machine on the internal Docker network, guarded by a constant-time shared-secret header, `401` without it. Not an anonymous data path. |
| `/actuator/health`, `/actuator/health/**` | Docker `HEALTHCHECK`.                                                                                                                                                                                          |
| `/error`                                  | Spring's error dispatch.                                                                                                                                                                                       |

Both anonymous reads are `GET`-scoped; a `HEAD` on them falls to the authenticated catch-all and
answers `401` (Spring compares the verb exactly, `SecurityTest:173–182`). The sweep of §6 is keyed
by (verb, path) for that reason.

The **prod-only management-port chain** (`ManagementPortSecurityConfig.java:57–58, 68–70, 93–101`,
`@ConditionalOnProperty("management.server.port")`, `application-prod.yml` port `11271`) is
`permitAll` on `/actuator/health(/**)`, `/actuator/prometheus` and `/actuator/info` on the internal
connector only (ADR-0134); `MonitoringScrapeSecurityConfig` (`:86–89`) adds basic auth on
`/actuator/prometheus`. Neither is anonymous access in the brief's sense; both are listed so that
REQ-SEC-052 is an exhaustive statement and `ManagementPortIsolationTest` is named as their pin.

Everything else is `authenticated()` at the URL layer **and** carries a method gate (WP-B 2 widens
the ArchUnit rule so this is enforced for every `GET` as well — today `AnnouncementController:57`,
`MaterialCategoryController:57, 68`, `TerminalController:67, 85`, `HangarController:101, 148` and
twelve `InventoryItemController` reads rely on the URL layer alone). The following matcher families
are **deleted** from the matrix: the whole catalogue block (`frequency-types`, `locations`,
`job-types`, `manufacturers`, `materials`, `refining-methods`, `settings`, `ship-types`,
`squadrons`, `star-systems`), the five mission `GET` rules, the mission `POST`, the ten participant
write rules, and `GET /api/v1/org-units/active`. `/v3/api-docs/**` moves to `hasRole('ADMIN')` (it
is already a 404 in prod).

### 2.3 Roles

- The `GUEST` role no longer exists: not in the backend `Roles`, not in the frontend
  `support/Roles`, not in `DataInitializer`, not in the database, not in either test realm, not in
  the provisioning script or its self-test, not in the issue templates, not in any document.
- An authenticated token whose realm roles map to **no** known application role is **refused**
  with `403 NO_ROLE` (Decision D5) — it is not silently promoted to member and it is not silently
  given an empty role set. The refusal lives in `assembleFor(User, Collection<Role>)` so that both
  the JWT path and the ingest gateway's acting-member path (`DatabaseActingMemberAuthorities`)
  yield it. The Keycloak realm's `default-roles-iri` composite already grants `KRT Member` to every
  new account (Decision D6) — and the roster sync must learn to read that composite before D5 ships,
  because today it reads directly-assigned roles only (§4.2, WP-B 7).
- `PENDING` / `REJECTED` registrations keep their single `ROLE_PENDING_APPROVAL` authority and the
  existing waiting page (REQ-SEC-017). Nothing below member exists any more.

### 2.4 Missions

- `is_internal` keeps its meaning **among members**: `false` = visible to every member of the
  organisation (the cross-Staffel escape of REQ-ORG-009 / the `Mission` scope kind), `true` = the
  owning unit and its leadership cascade only. In mission labels and documents „öffentlich" becomes
  „organisationsweit" (Decision D8); the *SK-public* job-order queue keeps its name, because there
  "public" already means "every profit-eligible Staffel", not "anonymous".
- There is no outsider redaction tier any more. The **member-peer** tier (a member below
  Logistician sees participants without e-mail and real name, REQ-SEC-007) stays and is renamed
  from `cleanup…ForGuest` to `cleanup…ForPeer`, together with the ArchUnit rule that enforces it.
- Guest participant rows stay as data (Decision D4, as decided): **any member who can see the
  mission may add** a named external participant — as a logged-in user can today — while editing
  and removing such a row is the mission leadership's (`canManageMission`), because an external row
  carries no creator to bind a self-edit to. The payout keys `guest_<name>` keep working; there is no
  anonymous self-service path and no capability token.

## 10. Risks and watch items

- **The composite-blind roster sync** is the one precondition that turns a security hardening into
  an outage if skipped: with D5 live and the sync unchanged, every member who holds `KRT Member`
  only through `default-roles-iri` would be refused after the nightly run until their next web
  login. WP-B 7's sync fix ships in the same PR as D5 and is pinned by §6.7.
- **401 spike alert noise**: scanners that got `200` on the catalogues now get `401`;
  `BackendAuthFailureSpike` may fire during the first days. Measure, then retune (WP-E).
- **Anonymous session growth**: HTML crawler hits on former public URLs still reach the OAuth2
  entry point and mint the 30-minute pre-login session; the public pages themselves no longer mint
  any. `ActiveSessionsRunaway` watches the count; the created-versus-login ratio is the first thing
  to compare if it fires.
- **A Guest-only production account**: after `V239` it has no role and is refused until an admin
  assigns `KRT Member`. The migration logs the ids; the owner can count them beforehand with a
  read-only `SELECT`.
- **The dangling `bearerAuth` scheme** is frozen into the Android contract; renaming it changes
  only documentation, not the wire, so no release ordering applies.
- **No plain revert after promotion** (D10/D12 as decided): the single PR drops the token column and
  deletes the `GUEST` rows in `V239`; a reverted image fails schema validation. The forward-fix
  branch of §8 is prepared before the promotion, and the promotion gate plus the `e2e` label are the
  safety net the slicing no longer provides.
- **Parallel PRs**: ADR-0159, `REQ-SEC-052/053` and `V239` collide with any sibling branch that
  takes the next number — claim at push time; a PR this large sits open long enough for the
  collision to be likely.
- **The `Request Authorization` KB note has an uncommitted local modification from another
  session**; the KB commits of this plan stage their files explicitly and never sweep it in.

  authorisation decision; the entry point redirects with `?prompt=none` and answers `401` to
