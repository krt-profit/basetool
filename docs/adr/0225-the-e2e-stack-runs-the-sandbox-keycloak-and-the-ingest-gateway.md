## Context

The exchange round trip — a third-party client signing a member in through the device grant, then
syncing through the ingest gateway with a DPoP-bound token, and the member undoing and disconnecting
it on „Verbundene Anwendungen" — could not run on the E2E stack. `E2eStackExtension` started six
services without the gateway, on the stock Keycloak image with a hand-written realm that had no
client scopes, no gateway service account and no third-party client, and that ran with its own
token and session settings (a 3600 s access token, rotated refresh tokens) rather than production's.

The local sandbox (#2196) already had all of it: the Keycloak image with the SPI and the `krt-theme`
(`docker/sandbox/keycloak/Dockerfile`) and a realm generated by `scripts/build-sandbox-realm.py` from
the E2E realm and the production provisioner. The question was whether the E2E stack should adopt
that Keycloak and generated realm, or keep its own and gain only the missing clients.

## Decision

1. **One generator, two realms.** `scripts/build-sandbox-realm.py` builds both realms from the
   shared base `scripts/keycloak/test-realm-base.json` (the roles, the two first-party clients and the
   E2E accounts) plus the provisioner's realm settings, login theme, client scopes, ingest gateway
   client and third-party template. The sandbox realm (`docker/sandbox/keycloak/realm-basetool.json`)
   replaces the accounts with the sandbox members; the E2E realm
   (`frontend/src/e2e/resources/realm-export.e2e.json`) keeps the E2E accounts and adds
   `e2e-exchange-client` and the account `test-exchange`. `--check` in `repo-lint.yml` fails when
   either committed file is stale, `--selftest` proves the invariants of both.
2. **The E2E stack runs production's realm settings.** Token lifetimes, session bounds, refresh-token
   handling and the login theme are the provisioner's `REALM_SETTINGS`; the generator refuses a realm
   that differs. No E2E test depends on the former 3600 s token or on rotated refresh tokens.
3. **The E2E Keycloak is the sandbox image.** `docker-compose.e2e.yml` builds
   `basetool-sandbox-keycloak` from its Dockerfile and mounts the E2E realm over the image's own
   realm file, so the SPI and the theme are exercised on every run. The SPI stays inert for password
   logins: the realm configures no Discord identity provider and no flow that calls the gate.
4. **The E2E stack runs the ingest gateway.** `ingest-dev` joins the stack with the gateway's
   audience and service account; the backend runs the exchange registry mirror.
   `ExchangeRoundTripE2eTest` drives the round trip in every browser × device cell.
5. **CI builds four images once.** `e2e.yml`'s `build-stack` job builds the ingest and the sandbox
   Keycloak images beside the backend and frontend, the two new ones in parallel with the two
   existing ones, and saves all four into the one archive the cells load.
   `E2ePrebuiltImageParityTest` keeps the workflow, the compose files and the extension naming the
   same four images.

## Consequences

- The E2E suite tests the login pages members actually see, the production token lifetimes and the
  exchange end to end; a change to the provisioner's settings or the theme now reaches the suite.
- The SPI jar is compiled in Docker once more per run. The uncached Keycloak build took about three
  minutes locally; it runs beside the backend and frontend builds, so the job's wall time barely
  grows. The image archive grows by the Keycloak and ingest images.
- The E2E realm is generated: a new E2E account or a change to the first-party clients goes into the
  base file, followed by `python3 scripts/build-sandbox-realm.py`.
- The sandbox and the E2E stack still share their fixed ports, so they cannot run at the same time.

## Alternatives considered

- **Keep the stock Keycloak and add the exchange clients to the E2E realm** (option B). Rejected by
  the owner: the E2E suite would keep testing a login theme and token settings production does not
  use.
- **Create the clients at runtime** through the Keycloak admin API or the provisioner (option C).
  Rejected: it either copies the provisioner's shapes into Java or adds Python to the Java harness,
  and the provisioner would rewrite the realm settings anyway.
- **Run the exchange E2E against the sandbox stack only** (option D). Rejected: the exchange tests
  would run on a different stack from the rest of the suite.
- **Build the Keycloak image from the Gradle-built SPI jar.** Not taken: `.dockerignore` excludes
  every `build` directory, so it needs a JDK in the `build-stack` job and a second Dockerfile path,
  while the Docker build already runs in parallel with the longer application builds.
