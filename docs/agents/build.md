# Build system

The Gradle build in full: the version catalog, refreshVersions, the repositories, the
`build-logic` conventions, the per-module settings, the configuration cache and dependency
verification. Read it before changing a build script, the catalog or a dependency.

Profit Basetool — a squadron-management web app (mission planning, hangar, inventory, refinery, user admin) for the "DAS KARTELL" organization. Three Spring Boot 4 applications (`backend`, `frontend`, `ingest`) on Java 25, plus the `keycloak-spi` provider JAR, the `keycloak-theme`, the shipped `logging-support` library and the test-only `test-support` library; PostgreSQL 18, Keycloak 26 OAuth2, Redis-backed Spring Sessions. Production runs as rootless Podman + Quadlet units generated from the compose files (arc42 §7); local and test stacks run on Docker Compose. Gradle 9 with Kotlin DSL. Dependency versions live in the **version catalog** at **`gradle/libs.versions.toml`** — edit that, not `build.gradle.kts`. [refreshVersions](https://jmfayard.github.io/refreshVersions/) runs in *catalog* mode and is applied **only on request**: `./gradlew refreshVersions -PrefreshVersions` annotates the catalog in place with `## ⬆ = "…"` comment markers for each available update and changes no version itself (without the flag the task does not exist — the plugin is kept off every other build because it is not configuration-cache compatible). **There is no `versions.properties`** (removed 2026-09-23): it held zero versions, and the refreshVersions run recreates an empty one that is gitignored. Repositories are declared once, in `settings.gradle.kts` (`FAIL_ON_PROJECT_REPOS`) — `dependencyResolutionManagement` for the module classpaths and `pluginManagement` for the plugin/buildscript classpath, which takes `gradlePluginPortal()` first and `mavenCentral()` behind it in both settings files, because the portal only redirects library artifacts to Central and is otherwise a single point of failure (REQ-OPS-046, ADR-0275); shared module conventions (toolchain, Lombok/JetBrains, Mockito agent, `spotbugsMain`, SBOM settings, …) live in the **`build-logic`** included build as `basetool.*` precompiled script plugins that each module applies by id in its `plugins {}` block (REQ-OPS-046, ADR-0248) — the root build has no `subprojects {}` block, and a precompiled script reads the catalog by alias (`Catalog.kt`, not `libs.…`) and copies a script-level `val` into a local before a task action or a provider lambda captures it. The per-module values those conventions apply — test heap, coverage floors, PIT targets — live in each module's **`build-settings.properties`**, and a missing file or key fails configuration (REQ-OPS-037); a new module declares its own instead of inheriting a default. The configuration cache is on for every build (`org.gradle.configuration-cache=true` in `gradle.properties`; CI also passes `--configuration-cache`), so a build-script change must stay configuration-cache compatible — check with `./gradlew help --configuration-cache` run twice (the second must say *reused*) and `./gradlew build -m --configuration-cache`. **Every artifact Gradle resolves is checked against `gradle/verification-metadata.xml`** (SHA-256, strict; ADR-0208, REQ-OPS-034): a change that alters what the build resolves — a catalog bump, a new dependency or plugin — regenerates it in the same commit with `GRADLE_USER_HOME="$(mktemp -d)" ./gradlew --write-verification-metadata sha256 help build :frontend:compileE2eJava` (details: CONTRIBUTING → *Dependency verification*).
